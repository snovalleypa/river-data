# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Goal: Create a public data repository of Snoqualmie River stream gauges from USGS and Floodzilla (an SVPA public benefit product) for various use cases including building models to provide more granular forecasts during flooding events.

Flood and river data analysis for the Snoqualmie River system. Pulls gauge readings from USGS and SVPA's Floodzilla API, detects flood crests, and aligns upstream/downstream crests to compute travel times.

## Definitions

- SVPA - Snoqualmie Valley Preservation Alliance; local non-profit that supports farmers with a focus on flood protection
- Floodzilla - A web site and flood gauges network in the Snoqualmie River Valley operated by the SVPA
- USGS - United States Geologic Survey; operates stream flow gauges in the Snoqualmie River and tributaries
- NWRFC - Northwest River Forecast Center; Part of the National Weather Service that is publishes forecasts for some of the USGS gauges on the Snoqualmie River.

## Setup

```bash
pip install -r src/requirements.txt
```

Use a virtualenv and run scripts via it — deps are not in system python:

```bash
python -m venv .venv && .venv/bin/pip install -r src/requirements.txt
.venv/bin/python src/fetch-gauge-data.py -y 2022-2026
```

`.venv` is gitignored. Scripts target modern pandas (2.x).

All scripts and notebooks assume the **repo root** as the working directory — they reference `locations.json`, `data/`, and `crests/` with relative paths and will silently misbehave if run from elsewhere.

When running a long script in the background, its stdout is buffered and won't appear incrementally — track progress via parquet/CSV file counts on disk instead of tailing the log.

## Pipeline

The scripts in `src/` form a sequential pipeline; output of each feeds the next:

1. **`fetch-gauge-data.py`** — Downloads readings for each station in `locations.json` into `data/{source}/{id}/{id}-{year}.parquet`. USGS data comes through `hydrofunctions` (stage + discharge); SVPA data comes from the Floodzilla `GetGageReadingsUTC` endpoint (stage only). `clean_write_data` normalizes columns so both sources have the same schema (`stage`, `stage_qualifiers`, `discharge`, `discharge_qualifiers`, `location`).

   ```bash
   python src/fetch-gauge-data.py -y 2001-2022           # all stations, all years in range
   python src/fetch-gauge-data.py -y 2022 -id SVPA-26    # one station, one year
   python src/fetch-gauge-data.py -y 2022 -s USGS        # all USGS stations
   ```

   `--floodyears` is a water-year range — water years run **Oct 1 → Sep 30**, named by the ending year (so `-y 2022` fetches `2021-10-01` through `2022-09-30`).

2. **`sum-forks.py`** — Joins the three USGS forks (South `12143400`, Middle `12141300`, North `12142000`) on their timestamp index, sums discharge, and writes a synthetic `FORKS` station to `data/usgs/forks/forks.parquet`. Only retains rows where all three forks have readings.

3. **`calc-crests.py`** — Iterates the stations in `locations.json` (in `stage` mode) and detects flood crests using a state-machine over sorted readings. The synthetic `forks` station is generated by a separate explicit `gen_crests('usgs/forks', measure='discharge')` call in `main()` because it isn't in `locations.json` and has no stage column. A crest is committed when:
   - A new high (`previous_max`) has been seen, AND
   - At least `gap_hours=18` have passed since that high, AND
   - The stage rose at least `stage_delta=1.0` ft above the trailing minimum (for discharge mode, the threshold is a 25% ratio).

   Tunable constants (`gap_hours`, `stage_delta`, `min_delta_ratio`, `measure`) are inline in `calc_crest()`. Output: `crests/{source}/{id}/{source}-{id}-crests.csv` (tab-delimited).

4. **`align-crests.py`** — Pairs each upstream crest to the nearest downstream crest within a 24-hour forward window, computing `crest_hours` (travel time). Hardcoded to align `crests/usgs/forks/usgs-forks-crests.csv` → `crests/usgs/12144500/usgs-12144500-crests.csv` (Falls). Output: `crests/aligned.csv`.

## locations.json

Single source of truth for every monitoring station. Each entry has `id`, `name`, `source` (`USGS` or `SVPA`), and optionally `upstreamOf`, `riverMile`, `stageOffset`. The pipeline scripts iterate this file rather than taking station lists as args.

## Notebooks

`notebooks/` holds analysis on top of the pipeline outputs (crest timing, peak annual height mapping, etc.). They read directly from `data/` and `crests/` and are not part of the automated pipeline. `data_files/historic-crest-overrides.json` is a manual correction layer consumed by the crest-analysis notebooks — keys are station IDs, values map event labels to `null` (suppress a false-positive crest) or `{"stage": X}` (override the detected value).

`notebooks/svpa-forecast-regression.ipynb` exports `data_files/floodzilla-predictions.json` (see its "Export predictions for Floodzilla" section). **The schema of this export is now consumed by code in the Floodzilla app.** Consumers tolerate *added* properties, so adding a field is safe; what breaks them is **renaming, moving, removing, or changing the type/meaning of an existing property** — avoid those unless necessary, as they require a coordinated change in the app. `schemaVersion` is a dotted `"major.minor"` string: bump the **minor** when adding properties, the **major** only for a breaking change to existing ones.

## Flood Visualizer (inundation map)

Separate from the gauge pipeline. The Floodzilla app's **Flood Visualizer** (the
"Map" tab) shows, per flood level, the inundation extent plus road-closure overlays.
That data is hosted on GCS (`gs://fz-dev-public`) and loaded by the app by URL;
`floodzuki_data/` is the **committed local mirror** of that bucket, and
`flood_extents/` holds the scripts that produce it.

- **`floodzuki_data/flood-viz-levels-region-<N>.json`** — region config: a `levels`
  array where each entry has a `key` (minor/moderate/major/…), `cfs`, an inundation
  `file`, and a `roadClosuresFile`. The generator iterates this, so **adding a level
  needs no code change** — add an entry (and the matching FloodExtent file).
- **`floodzuki_data/FloodExtent_<cfs>CFS_fixed_simplified.geojson`** — inundation
  polygons per level. Produced from raw ArcGIS exports by
  **`flood_extents/fix_and_simplify.py`**, which fixes exterior-ring winding
  (ArcGIS CW even-odd → RFC 7946 CCW) and simplifies via `npx mapshaper`.
- **`floodzuki_data/floodzilla_roads_region_<N>.geojson`** — the **single
  maintained source** for road closures. Each road is one `LineString` feature whose
  `status` property is a *map* keyed by level, e.g.
  `{"minor": "nearFlooding", "moderate": "flooding", "major": "flooding"}`. Valid
  statuses: `normal`, `nearFlooding`, `flooding`. Do **not** hand-edit the per-level
  RoadClosures files — they're generated.
- **`flood_extents/generate_road_closures.py`** — reads the source + region config
  and writes one `RoadClosures_<cfs>CFS.geojson` per level into the publishable
  bundle **`floodzuki_dist/`** (gitignored), alongside copies of the config and each
  level's FloodExtent file. The per-level caption is derived from status:
  `normal`→"Open", `nearFlooding`→"Possible Closure", `flooding`→"Closed". A road
  omits a level it has no status for. Run from the repo root:
  `python3 flood_extents/generate_road_closures.py` (`--region`, `--data-dir`,
  `--dist-dir` configurable).
- **Publish:** upload `floodzuki_dist/` to `gs://fz-dev-public`. The app colors each
  road line from its `status` (no color in the GeoJSON) and reads the caption from
  `label`. The `add-flood-visualizer-road` skill automates adding/updating one road
  (fetch OSM geometry → upsert into the source → regenerate).

## Data layout

`data/` and `floodzuki_dist/` are **gitignored** — `data/` is regenerated via
`fetch-gauge-data.py`, `floodzuki_dist/` via `generate_road_closures.py`. `crests/`,
`data_files/`, and `floodzuki_data/` (the inundation-map mirror) are committed.
